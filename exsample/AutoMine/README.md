# AutoMine

Baritone（Java版）風の自動採掘クライアントMod。対象ブロックを指定すると、付近を探索して歩いて近づき、最適なツールに持ち替えて掘り続ける。

## 使い方

| コマンド | 動作 |
| --- | --- |
| `/mine <ブロックID>` | 採掘開始（例: `/mine iron_ore`、`/mine stone`、`/mine oak_log`） |
| `/mine <ブロックID> <個数>` | 個数ゴールを付けて採掘開始（例: `/mine diamond_ore 10`）。ドロップ換算で数え（ダイヤ鉱石→ダイヤモンド等）、開始時点の所持数からの増加分が目標に達したら「目標達成」を表示して停止する |
| `/mine status` | 現在の状態をチャットに表示 |
| `/mine path` | 経路表示の ON/OFF 切替 |
| `/mine stop` | 停止（合成入力は全て解放される） |

ブロックIDはローカル名（`minecraft:` なし）で完全一致。見つからない場合は約2秒間隔で再探索するので、歩き回れば新しいエリアでも掘り始める。

コマンドは SDK の `NativeInjectedCommands` でクライアントの補完候補へ追加し、ローカル実行する。状態確認は `/mine status`。

## 仕組み

実装は `src/auto_mine.hpp` に宣言と共有状態を置き、責務ごとのcppで定義する。
`controller.cpp` がtickと状態遷移を統括し、各機能の処理を呼び出す。

| ファイル（`src/`） | 責務 |
| --- | --- |
| `auto_mine.cpp`, `runtime.cpp`, `diagnostics.*` | DLL起動、設定、SDK初期化、ログ・例外記録 |
| `controller.cpp`, `screens.cpp` | コマンド、tick、画面状態 |
| `controls.cpp` | 独立入力、照準、位置・ブロック・遮蔽の問い合わせ |
| `target_selection.cpp`, `pathfinding.cpp` | 採掘対象の選択、地形評価、経路探索 |
| `navigation.cpp`, `construction.cpp`, `boat.cpp` | 経路追従、橋・足場・パルクール、ボート移動 |
| `path_render.cpp` | 将来の行動列と経路・破壊進捗の描画 |
| `mining.cpp`, `tools.cpp`, `block_knowledge.*` | 採掘・回収、道具選択、ブロックと道具の知識 |
| `inventory.cpp` | 所持品読み取り、ホットバー移動、整理・投棄 |
| `crafting.cpp`, `crafting_table.cpp`, `smelting.cpp` | 合成チェーン、作業台の設置・利用、精錬 |
| `excavation.cpp`, `expedition.cpp`, `forage.cpp`, `recovery.cpp` | 昇降、素材調達の統括、食料調達、復帰・水中対策 |
| `combat.cpp` | 周囲のアクター探索と戦闘 |

地形・行動計画・所持品方針の純粋な処理は `action_plan.hpp`,
`navigation_geometry.hpp`, `locomotion_geometry.hpp`, `inventory_policy.hpp` に分離している。
共有ヘッダーはプリコンパイルし、各cppを独立したコンパイル単位としてビルドする。

- **探索**: 距離・高低差・周囲の掘削負荷で対象を評価する。鉱脈は接続した最大32セルを保持し、回収後は残りの鉱石へ進む。到達不能や進捗のない対象は一定時間避ける。
- **移動と照準**: 既定の `independent_control: true` では、SDK がゲームのシミュレーション呼び出し中だけ移動コンポーネントを借り、終了時に元の値へ戻す。画面の向きに対して移動ベクトルを変換するため、カメラを回しても自動移動の方向を保つ。採掘は GameMode の開始・継続・停止を呼び、送信される移動パケットの照準を自動作業方向へ合わせる。カメラや位置・速度への書き込み、移動用の合成キー・合成マウス入力は使わない。WASD・ジャンプ・スニーク・スプリント・左右クリックの手動操作中と、その解放後750msは自動作業を休止する。`continue_in_chat: true`（既定）の場合はチャット画面が開いている間も採掘・移動・回収を継続し、チャット入力中のキーと自動制御を競合させない。`background_crafting: true`（既定）ではサーバー側のコンテナを要求し、ボットが要求した作業台・インベントリ・かまどの画面表示を抑えて裏で処理する。チャットを閉じるキーは送らない。画面を使う従来経路はこの設定をfalseにした場合だけ使い、チャット中は待機する。ポーズ・設定画面では停止する。独立制御はウィンドウが裏に移ってもレベル tick が継続する限り動作する。裏クラフトが失敗しても画面を奪う方式へ自動切替はしない。`false` は従来のキー・マウス制御に戻す。
- **水中ガード**: 上方向（最大16セル）に水があるブロック（海底の土や、その下に埋もれた土）は対象から外す（泳げないため追うと溺死ループになる。湖の下の乾いた洞窟なども安全側に倒して外れる）。設定 `skip_underwater`（既定 true）で切替可。
- **溺死セーフティネット**: 作業中（移動・採掘・回収・ツール待ち）に頭が水没した状態が続くと、対象を諦めてジャンプ長押しで浮上し、頭が水から出たら探索を再開する。脱出した場所の周囲（半径6）はハザードゾーンとして以降の対象選定から外れるので、岸壁沿いを脱出→再選択で延々と辿ることもない。対象選定をすり抜けた水中スタンドポイントでも溺れないための最終防衛線。
- **経路表示**: 歩行・掘削・設置を順序付きの計画にして描く。移動は緑、掘削は黄、設置はシアン。各作業セルのマーカーと進行方向の矢印を表示し、採掘中・回収中・ツール待ちも残りの経路を保持する。縦掘りは指定高度まで、横掘りは現在の6セルの区間まで、読み取れた地形の先の作業を表示する。未知の地形・水/溶岩・掘れない障害物で確認済みの計画を止める。`/mine path` で切替。1.26.60.5では従来からレンダラーの色反映に問題があり、黒い線になる場合がある。
- **経路探索（A*）**: 最大4セグメント・合計72,000展開の探索で目標に接続する。歩行・段差・落下・掘削・橋・ギャップジャンプ・1ブロック高い壁越しジャンプ・足場登りを評価し、移動セルを省略せず保持する。パルクールはアプローチ→助走→離地→空中補助→着地確認の状態機械で実行し、横壁や足元の足場ブロックも補助配置する。失敗や長時間滞空ならパルクールセルをブロックし、経路を再計算する。軌跡は放物線として表示する。掘るために止まる位置と掘削後に歩く位置を分離し、高所鉱石への掘り抜き中も元の目標を維持する。掘削や登りの直前では先読みを止め、通過していない段差を飛ばさない。
- **橋渡し（ブリッジ）**: 経路探索は、床が抜けているが足場ブロックを置けるセルを「橋セル」として扱う（徒歩より高く掘削より低いコスト、横方向のアンカーから最大3マス幅まで連鎖して計画）。ホットバーに余りブロック（丸石・土・石など、砂利や砂などの落下ブロックと板材は除く）がある場合のみ有効。追従側は橋セルの手前で立ち止まり、遠い側から順に足場を置いて埋まったことを確認してから渡る。射程外の場合は床の有無を確認しながら縁まで慎重に近づき、最後の1マスはジャンプしながら真下に置く。置けない・届かない場合はその橋を諦めて迂回路に組み直す。
- **水泳**: 陸ルートが無い対象へは水面を泳いで渡る。移動は頭が水面に出ている時だけ進み、頭が沈んだらまず浮上を優先する。張り出し（天井）の下に潜り込んだ場合は、上昇しながら後退して抜ける（実証中に実際に溺れかけた罠への対策）。岸に着いたら陸から再計画する。採掘・回収中は水面に留まるようジャンプを保持し、水中の足場で固まる場面には溺死セーフティネット（Escape）が引き続き効く。
- **採掘と回収**: 対象への射線を確認して採掘する。回収は安全な立ち位置を巡回し、到着して少し待つ。詰まった候補は飛ばし、インベントリ増加を確認する既存の回収判定と組み合わせる。
- **AutoTool**: ブロック種別（ツルハシ/斧/シャベル/クワ/ハサミ）と必要素材ランクから、ホットバー内の最適ツールを自動選択する。ホットバーは剣を左端、斧を左から2番目、ツルハシを左から3番目、シャベルを左から4番目のスロットへ優先配置する。不要品の投棄はメインインベントリだけを対象にし、既定では種・花などの限定リストを使う。ホットバー、採掘対象、基本材料、ツールは保持する。サーバー応答で投棄後の個数を確認する。**収穫ティアのゲート**: 鉱石ごとに「掘ってドロップが得られる最低ティア」が決まっており（ダイヤ/エメラルド/金/レッドストーン鉱石は鉄以上、鉄/ラピス/銅は石以上、黒曜石/古代の残骸はダイヤ以上）、ティア不足のツールでは採掘を一切開始しない。不足している場合は必要素材をチャットで知らせ、素材がインベントリにあれば下記のチェーンでそのティアのツルハシを自律的にクラフトしてから再開する。
- **AutoCraft（実クラフト）**: 使えるツールがインベントリに無い場合、SDK の `NativeItemStackRequests` アダプタで実際にクラフトする。レシピ表はサーバーから届く CraftingData をそのまま使い（レシピID・生成物の記述子を転記）、本物のクライアントの手作業フロー（グリッドへ配置→`craft_recipe`→結果をカーソルから全量しまう）を ItemStackRequest パケットで再現する（`craft_recipe_auto` は自前BDSが切断してくるため使わない）。ツルハシ用チェーンは「板材→棒→作業台→設置→木のツルハシ→丸石を3つ採掘→石のツルハシ」まで全自動で、対象の必要ティアが鉄以上の場合は鉄インゴット×3（ダイヤの場合はダイヤモンド×3）がインベントリにあれば木・石の段階を飛ばして鉄/ダイヤのツルハシを直接クラフトする。丸石集めで作業台から離れた場合は手持ちの作業台をその場に置く（無ければ板材4枚で新規に作る）。グリッドへの配置は画面（インベントリ等）が開いていないとサーバーが拒否する（status 49）ため、チェーン側で画面の開閉も行う。なお自作リクエストへの応答はクライアント自身のインベントリモデルに反映されないため、アダプタが応答から追跡したスナップショットを正として持ち物を読む。材料不足やクラフト失敗時は従来どおり手順をチャットで伝えて待機し、ツールが現れたら自動で再開する。
- **戦闘**: 作業中に敵対Mobが近づくと（水平・垂直とも近接、または至近距離）中断して応戦し、倒したら作業に復帰する。Mob種別はアクターの型コンポーネントから判定する（1.26.60.5実機で召喚検証したID: ゾンビ199456・スケルトン1116962・クモ264995・クリーパー2849、ほかゾンビ系2種）。剣 > 斧の優先でホットバーから最適武器を選び、リーチ（目線からMobのAABBまで約3ブロック）と視線（ボクセルレイキャストで遮蔽チェック）が通った時だけ攻撃する。クリーパーには弓があれば距離を取って射撃し（独立制御時の引き絞りはGameModeのアイテム使用）、弓が無い場合は一撃ごとに後退して爆発を回避する。武器が何も無い相手がクリーパーなら逃げる。届かない相手（高所・水底など）は一定時間で諦めて1分間無視するので、戦闘と浮上のループにはならない。`/mine mobs` で周囲アクターの読み取り値をログに出せる（種別判定のデバッグ用）。
- **ボート（従来制御のみ）**: 独立制御は車両入力を扱わず、水泳経路を使う。従来制御では長い水の横断（対象まで10ブロック超）でホットバーにボートがあれば、まずボートを水面に出して渡りを試みる（対象ごとに1回だけ）。設置は新規に現れた船体（アクター型90）でのみ確認する（ボートはワールドに残り続けるため、以前の試行の残骸を「今置いた」と誤認しない）。乗船は使用ボタンのパルスで行い、成立の判定は「甲板の高さへのロック」と「船体に密着した状態で漕いでみて船が付いてくるか」の行動プローブの二段構え。乗れたら視点で操舵して対岸近くでスニーク下船する。各段にタイムアウトがあり、失敗したら通常の水泳にフォールバックする。**ボートのクラフト**: ボートを持っていない場合は、岸で AutoCraft により「板材→作業台→設置→ボート」をクラフトしてから渡りを試みる（対象ごとに1回だけ。材料が無ければそのまま泳ぐ）。**乗船について**: 当初は自動テスト環境（BedrockOnLinux/Wine）で使用ボタンのフィード入力が「乗る」判定に届かず乗船が成立しなかったが、2026-11-16 の実証では岸から出艇する形で2回連続で乗船・航行・下船まで成立した（船体がプレイヤーを 5.3 / 3.9 ブロック運んで判定）。長距離では操舵がタイムアウトして途中で下船し、残りを泳いで完走する場合がある。実機Windowsでの挙動は未確認。

## 検証範囲

独立制御用のネイティブ情報は1.26.65.1/1.26.60.5の実行ファイルを静的解析した候補で、SDKの版別プロファイルと入口バイト検査で管理する。旧版Solsticeのオフセットは使用しない。現行の入力フラグは [LeviLaminaのMoveInputState定義](https://github.com/LiteLDev/LeviLamina/blob/main/src/mc/input/MoveInputState.h) と実行ファイルの読み出しマスクを照合した。

今回の確認はDLLのコンパイル、行動計画・移動座標変換・パケット編集の単体テスト、プロファイル整合性まで。ゲーム内の独立制御、採掘・配置・戦闘・クラフトの動作確認は未実施。プロファイルも `runtime_verified: false` のままとしている。

チャット中の継続は `continue_in_chat` で切り替える（既定true）。メニューでは停止し、手動移動・クリックを優先する。従来制御（`independent_control: false`）では視点とキー入力を操作し、マウス捕捉が必要。

## r4の回収と軌跡

原木・土なども、採掘前の所持数を基準に回収を確認する。回収地点への移動は床と頭上空間を調べた有限探索を使い、壁の迂回・1段登り・最大3段の降下を計画する。実行する回収経路をそのまま表示し、通常ルートの登りはジャンプ、降下は縁から着地点への線として描く。未探索の場所への直線を確定経路として描かない。到達不能やタイムアウトは未確認として記録し、回収済みとは扱わない。

独立採掘は物理マウスの押下を共有しない。GameModeの時計が進まない場合はゲーム自身の時計更新を呼び、実際の破壊進捗を読む。対象ブロックは常にオレンジの外枠で示し、破壊中はブロック中央に小さな黄色のBoxを表示して進捗に合わせて外枠いっぱいに拡大する。進捗やブロックの消失を自前で生成しない。これらの実機動作は未検証。

## r6: 裏クラフト・経路・道具整理

`background_crafting` は既定true。REA/Ghidraで確認した現行版のInteract要求とContainerOpen/CloseのディスパッチャーをSDK内で扱い、要求した種類・座標に一致するコンテナだけを所有する。画面・文字入力を開閉せず、既存のItemStackRequestチェーンで合成する。ユーザーがインベントリや設定画面を開いている間はジョブの送信を待機する。成功・失敗はサーバー応答で判断し、失敗時にEsc/Eへ切り替えない。新しいネイティブ定義はcandidateで、裏クラフトの実機確認は未実施。

r10では作業台・かまどの裏設置を、押し続ける右クリックから指定セルの床面への単発配置に変更した。設置後のブロックへ使用入力が流れず、裏設置中にEscも送らない。所有中の同一コンテナから重複した開封応答が届いても画面へ渡さない。汎用の使用経路が作業台・かまどに当たった場合も、裏コンテナの応答待ちを先に設定する。実機での画面非表示・文字入力との併用は利用者側で確認する。

### r11 (`automine-fixes-20261119-r11`)

- 作業台・かまどは支持面と見える設置面を毎回確認し、実際に確認した面へ単発配置する。失敗セルは実行中の除外集合に入れ、同じ場所へ戻らない。掘ったポケットにも同じ条件を適用する。
- ユーザー画面の表示中は背景コンテナの開始・終了送信とクラフト処理を待機する。通常移動からユーザー画面をEscで閉じる処理も削除した。
- クラフト応答の所持品を、ネイティブ読み取りが未準備のスロットでも保持する。bootstrapの既存テーブル再利用を維持し、ツルハシ経路と実際のクラフト直前にも重複作成を防ぐ。
- 適正ツールは必要ティアを満たす低ティア→同ティアで耐久の少ないもの→同条件なら現在スロットの順。SDKの既存プロファイルにあるauxから摩耗を読み、バックパックからの補充も同順にする。応答で確認済みの道具はネイティブ名の遅延だけでは捨てず、未反映時には再クラフトせず同期を待つ。
- ポケット掘り完了時に攻撃入力を解除し、設置スロットと採掘ツールの選択競合を防ぐ。RecoverとAscendの帰還経路・掘削・柱上りも通常の軌跡描画へ渡す。
- チャット入力のキー解放も手動移動と区別する。ジャンプはMoveInputComponentの入力flagsとheldミラーの両方へ反映し、エッジflagsだけはミラーへ渡さない。
- 足場・橋・柱の供給を共通化し、不要な地形ブロック→石材→板材の順。バックパックの不要ブロックも板材より先に使う。原木・木・幹・菌糸を直接設置せず、最後の手段として板材クラフトを挟んで元の移動へ戻る。

#### 問題H: パルクールのスプリントジャンプ（build IDはr11のまま）

- 1〜3マスの溝すべてで助走床を要求する。助走位置への移動は歩行、前向きの助走はスプリントとし、接地・踏切位置・進行方向速度0.12以上を確認して踏み切る。独立制御では、SDKが前進＋スプリントを入力flagsとheldミラーへ適用したsimulation呼び出しを2回以上確認する。
- 独立制御の専用経路では、SDKが既存プロファイルのactor yawをsimulation中だけ進行方向へ借用し、終了時に復元する。カメラ基準の横・後進へ変換された入力ではなく、前進とスプリントでゲームのジャンプ処理へ渡す。通常歩行のカメラ相対制御は変更しない。新しいオフセット、速度・座標の直接書き換え、疑似ジャンプは追加しない。
