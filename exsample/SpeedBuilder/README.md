# SpeedBuilder (Windows x64 example)

Hiveの記憶・再現ゲーム向けの候補実装です。自動記録・配置の候補実装は **1.26.52.3**。
**1.26.60.5はタイトル観測モードです。自動記録・自動配置はまだ動作しません。**
共通`Packet::read` HookでID 88の通信データを読み、native SetTitlePacketのフィールドには依存しません。
ログの`Packet read counters`と`title received [observer]`で受信を確認できます。
ホットバー選択・配置状態計算・HitResultの新ABIは調査中です。
Titleのお題が空でなく、Subtitleに `記憶しましょう` を含むと記録を始めます。
ゲーム内での受信Hook・配置・向き・サーバー受理は実機未確認です。

## 動作

1. プレイヤーを中心に半径10ブロックの立方体を、tickごとに分割して記録。
2. 記録したブロックが消えたら元の記録を固定し、消失後の差分をワーカーで作成。
   完全な2回の観測で消失差分が一致し、ホットバーに対応ブロックの増加を確認して配置へ進みます。
   元から残っている床・建物は対象外です。
3. 各対象について、実際のホットバーブロックのaux、置く面、向き、クリック位置を使い、
   ゲームの配置状態計算APIが返す状態と記録を比較。
4. 一致する条件が見つかったら、ゲームの `PlayerInventory::selectSlot` でメインハンドを切り替え、
   実際のプレイヤーの向きも合わせて1tick待機。
5. 対象・支え・手持ち・距離・向き・ワールドを再確認して、メインハンド指定で
   `GameMode::buildBlock` を呼びます。通常の取引・配置パケット生成経路を利用します。
6. 配置後にブロック状態を観測して進捗を更新。失敗は最大3回、全体は時間制限付きです。

向き合わせは実プレイヤーの回転を使用するため、視点が一時的に動きます。
プレイヤーが途中で向きやスロットを変更した場合は、その変更を上書きして復元しません。
配置中に使った通常の回転・選択は、同じActor／RuntimeID／ワールドの場合だけ復元します。
ワールド変更・ディメンション変更・Actor変更時は記録と作業を破棄します。

## 導入・設定

独立ビルド時のSDK既定参照は `main` です。
MSVC Release x64でビルドした `BedrockSpeedBuilder.dll` をロードします。
初回はEscメニューを開いてゲームへ戻り、SDKへClientInstanceを認識させてください。

- 設定: `Documents\PEXData\SpeedBuilder\config.json`
- ログ: `Documents\PEXData\SpeedBuilder\SpeedBuilder.log`
- 中止: **Esc**（既定）。メニューを開いたときも中止します。
- 設定変更: 約500msごとに読み込み直し、進行中の作業は中止します。

```json
{
  "config_revision": 2,
  "enabled": true,
  "radius": 10,
  "max_blocks": 512,
  "capture_cells_per_tick": 1024,
  "build_interval_ticks": 1,
  "max_reach": 4.5,
  "max_attempts": 3,
  "confirmation_ticks": 20,
  "max_steps_per_tick": 8,
  "max_wait_ticks": 2400,
  "max_build_ticks": 2400,
  "prompt": "記憶しましょう",
  "keys": { "cancel": 27 }
}
```

## 負荷・制約

- ゲームメモリの取得・操作はクライアントのtickだけで行います。
- ワーカーは所有するコピーの差分整理、ログ書き込み、設定読込を担当します。
- キャプチャは設定上限（既定1024セル/tick）かつ初回約2000µs・後続約1000µsの協調予算。未処理分は次tickへ持ち越します。
- 配置状態の探索は最大64候補/tickかつ約1500µsの協調予算。
  単一のネイティブ関数が長くかかる場合、予算を超える可能性があります。
- 待機中に新しいTitleがなければホットバーを毎tick走査しません。
- 通常の到達距離以内の支えが必要です。記録半径10と配置距離4.5は別の設定です。
  移動の自動化はなく、遠い対象にはプレイヤーが近づく必要があります。
- 状態を再現する条件が見つからない対象は誤配置せず、`placement unresolved` を記録します。
- ブロックエンティティのNBT内容、額縁等のEntity、カスタムアイテム固有動作の再現は含みません。
- 名前はブロックの識別子を使い、Stateはワールド内の不透明な識別トークンとして比較します。
  ワーカーはそのトークンをポインタとして参照しません。
- `observed` はクライアントが記録状態を観測した数です。サーバー受理のACKではありません。
- ネイティブ定義はcandidateです。対象EXE指紋・関数入口・vtableの不一致で停止します。
  `SetTitlePacket` のストリーム読取が実際の受信経路を通るかも、ログによる実機確認が必要です。

## 実機ログを受けた修正（native revision 2）

- 予測前に対象アイテムをメインハンドへ選択し、1tick待ってから予測します。
  選択は予測中保持し、中断・失敗時は同一World/RuntimeIDで自動選択が残っている場合だけ戻します。
- ブロック付きItemStackの補助値はゲーム本体と同じくBlockのデータを使います。
  raw auxが0x7FFFの場合はその特殊値を保ちます。
- 向きは配置を実行するtickで適用します。準備時の向きが次tickまで残ることを条件にしません。
- solidではない足場候補も、ネイティブの衝突形状がある場合は候補に含めます。
  記憶範囲全体で衝突形状を取得せず、配置付近だけを調べます。
- 複数の足場がある場合は近い打点を選択します。通常のリーチ制限は維持します。
- 日本語UTF-8中の0xA7を装飾コードとして削除していた文字化けを修正しました。
- 同じ内容のconfigを保存し直すだけではラウンドを中断しません。
- 時間切れ・採点開始などの字幕で前ラウンドの配置処理を中断します。

診断ログ:

- `build hotbar`: 使用可能なスロット・識別子・個数・補助値。
- `placement pipeline`: `no_support`（足場なし）、`out_of_reach`（届かない）、
  `missing_item`（アイテムなし）、`last_defer`（実行前に見送った理由）。
  visitedなどの選択カウンタは直近の候補探索、native_callsなどはWorld内の累積です。
- `placement unresolved`: 予測の呼出数、失敗数、状態不一致数、予測・記憶したブロックデータ。
- `placement native`: 本体関数を呼べたか、戻り値が成功か。これはサーバー受理ACKではありません。
- `world identity ... changed=`: キャッシュをリセットした識別条件。

自動移動は行いません。記憶範囲10blockと、現在位置からの配置リーチは別です。
`out_of_reach`の場合は対象へ近づく必要があります。全種類の向きやサーバーでの
配置受理は実機確認待ちです。古いキャッシュ定義はrevisionを見て内蔵定義へ切り替えます。

## 接続状態・重ね置き（native revision 3）

ホットバー0～8の記録ブロックに対応するスロットを探索します。砂岩の壁の接続状態など、
配置後に変わる状態を配置前の予測と完全一致させる条件を改めました。同じ種類を通常の
メインハンド操作で配置し、実際のワールドで記録状態へ到達するまで確認を続けます。
`observed`は従来どおり完全一致した数で、種類だけ置けたものは`provisional`です。
接続が未確定でも、実際に存在して衝突形状のある同種ブロックを足場として使えます。

記録ブロックのNBT statesは有効な型・名前・有限のツリーを確認できた場合だけ読み、
方向などのプロパティを予測の選択に使います。カスタムブロックも同種の配置案を試しますが、
サーバー独自の回転・状態更新が期待どおりになるかは最終状態で判定します。
`placement deferred-state proposal`のexpectedに記録プロパティが出ます。
`unavailable`はプロパティ配置を検証できなかった場合で、未知のビットを向きと推測しません。

candles/cluster_countが示す重ね置きは、実際の同種ブロック・現在個数が記録より少ない場合に
追加操作します。個数が進んだことを確認してから次を使い、未確認の連打はしません。
単なるnative戻り値や、種類だけの一致を「完成」にしません。サーバー固有状態の完全再現は
実機確認待ちです。自動破壊・インベントリやサーバー状態の直接書換えは行いません。

## revision4: 配置開始待ちの修正

周辺の流体・壁接続などの状態変化や空気からの追加は差分対象から除外し、別の位置で観測した「ブロック→空気」を却下しません。
消えた全種類へのアイテム支給を待つ条件を変更し、対象に対応した支給を一種類以上確認すると配置を開始します。
不足アイテムは既存スケジューラーで待機し、別スロットの利用可能な対象から処理します。追加・置換された位置は破壊・上書きしません。
2回の除去確認、メインハンド選択、通常の到達距離、配置後の状態確認は継続します。
`build wait`に待機理由・差分状態・除外数、`waiting hotbar`に全スロットの取得結果を5秒ごとに出します。

## revision5: 大きな半径の開始待ちと角度保持

- 初回は中心に近いマスから読みます。以降は初回にブロックだったマスだけを観測し、空気を含む全立方体を繰り返し走査しません。
- 除去候補の2回目の確認は候補座標だけを再読します。最大128マス/回・協調1500us予算で分割し、読み取り不成立や再出現したブロックを配置対象にしません。
- 大きな初回スナップショットのworker向けコピーはラウンド中に一度だけ作り、後続ジョブで共有します。モデルへのアクセスとネイティブ読み書きはclient tickのままです。
- 旧既定値256マス/tickを1024へ、配置間隔2tickを1tickへ移行します。初回読み取りは協調2000us、後続は1000usです。既定と異なる設定値は維持します。
- スロット選択後、配置角度を準備tickから次のclient tickまで保持してから通常配置します。予測時だけの一瞬の角度変更で終わらせません。解除時は所有中の角度だけを復元します。
- `state mismatch`へ座標・expected/actual、`placement native`へyaw/pitch/face/support、各ログへ`at_ms`を追加しました。状態が一致しないブロックを完成扱いにはしません。

半径20は68,921マスなので初回の読み取り量は増えます。見本が消える前に初回記録が完了する必要があります。
初回に空気だったマスへ後から出現する見本パーツはこの方式では追加記録されません。サーバーの見本出現順によっては開始タイミングの追加調整が必要です。
Hive独自の`custom:facing_direction`とyawの対応は未確定です。角度保持でその対応表まで確定したとは扱いません。
残る向き違いは`state mismatch`と`placement native`の両ログで比較します。今回の実配置・サーバー角度反映は実機確認待ちです。


## 同種アイテムの配置プローブ

配置プローブは、記録したブロック状態とホットバーの `BlockType` が同一ポインタでない場合でも、
識別子が一致すれば候補として検証します。状態オブジェクトのポインタ一致は、配置後の厳密な状態確認に
引き続き使用します。


## revision6: 座標に対応する状態・向きの修正

- 中心から取得する配列と、従来の座標添字計算が食い違い、別座標の状態を参照する不具合を修正しました。座標→取得位置の対応表を作り、読み出し時も保存座標と一致することを確認します。
- 空の`properties={}`だけでは配置条件の一致と扱いません。ハーフ・階段・原木・樽などは正しい状態を予測できた候補を使います。壁・フェンス・板ガラス等の隣接依存だけ、配置後の状態確定を許可します。
- 回転候補はユーザーの一瞬の視点に依存させず、四方向と上下の候補から探索します。完全一致した配置方法はキャッシュし、他の座標でも支持面・距離・実予測を再確認して使います。
- 正しい状態を予測できない場合は誤った状態で強行せず、20tick後に再試行し、その間は別のブロックを処理します。支持ブロック待ちだけで試行回数を使い切りません。
- 最初の全体記録の後に一度だけ追加の全体走査を行い、遅れて出現したパーツを拾います。その後は非空気マスだけを観測し、見本が消える前に安定した状態を更新します。消え始めた観測で見本を上書きしません。
- 状態ログには元のプロパティと未解釈の`legacy_data`、`state_identity`を出します。数値のビットから向きを推測してはいません。

配置探索は最大48候補/回・協調1500us、取得は既存の協調1ms予算です。単一のネイティブ呼び出しが予算を超える可能性は残ります。
範囲外・支持面不足は移動や別のブロックの設置を待ちます。サーバー独自状態を通常操作で再現できない場合も待機ログを出します。
今回の実機配置、サーバー反映、全ブロックの向きは未確認です。`await_exact_state_or_support`や`placement unresolved`が続く場合はその行を含むログで切り分けます。

- ハーフ・階段などの支持面を「完全な立方体ではない」だけで事前除外せず、ネイティブ予測で配置状態を確認します。空気・未取得の支持面は使用しません。

### SDK共通World API

ブロック値型・ガード付きBlockSource読取・状態属性・配置予測・ホットバー選択・
本体配置呼出しはSDKへ移動しました。`src/native.hpp`は互換エイリアスのみです。
参照先は [World / Block / Camera API](../../docs/world-block-camera-api.md)。
ラウンド検出・配置順序・段階的探索のスケジューラーはSpeedBuilderが担当します。
