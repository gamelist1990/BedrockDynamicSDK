BUILD ON A STABLE INTERFACE

読みやすく、
間違えにくいAPI。

Minecraft Bedrockのネイティブ処理を、型付きのC++ APIから。プロファイルの選択と取得はSDKへまとめ、Modごとのバージョン依存コードを減らします。

名前・引数・スロット・角度を区別。暗黙の変換や引数の取り違えを防ぎます。

02 / PROFILE

更新処理を一箇所へ

EXE指紋、キャッシュ、GitHub、埋め込み定義をProfileManagerが扱います。

03 / LIFETIME

実行場所を明確に

native操作は所有tickで。workerへはコピー済みの値を渡します。

対応範囲 同じABIを使うゲーム版はプロファイル追加で対応しやすくなります。ABI・EnTT・構造の形が変わる場合はSDK側の更新とModの再ビルドが必要です。未知の版を自動で安全と判定する仕組みではありません。

GET STARTED

導入と初期化

Windows x64 / MSVC Release / C++20がnativeアダプターの対象です。Worldを使う場合は、SDKのFetchContent取り込み前にオプションを指定します。

set(BEDROCK_SDK_BUILD_TOOLS OFF CACHE BOOL "" FORCE)
set(BEDROCK_SDK_ENABLE_NATIVE_WORLD ON CACHE BOOL "" FORCE)
FetchContent_Declare(bedrock_sdk
    GIT_REPOSITORY https://github.com/gamelist1990/BedrockDynamicSDK.git
    GIT_TAG main)
FetchContent_MakeAvailable(bedrock_sdk)
target_link_libraries(MyMod PRIVATE bedrock::world)

コマンド登録・ProfileManagerだけなら bedrock::sdk をリンクします。EnTTは不要です。再現可能な配布ビルドでは、GIT_TAGを検証したコミットに固定してください。

#include <bedrock/profile_manager.hpp>
#include <bedrock/native_world.hpp>

bedrock::ProfileManager profiles;
bedrock::NativeWorld world;
std::string error;
const bedrock::ProfileOptions options{
    bedrock::UpdatePolicy::RefreshIfNeeded,
    bedrock::CandidatePolicy::AllowCandidates
};
const bool ready = profiles.prepare(
    {bedrock::Feature::World}, options,
    [&](const bedrock::RuntimeProfile& selected, std::string& failure) {
        return world.load(selected, failure);
    }, error);
if (!ready) { /* errorをログへ。機能を有効にしない */ }

prepare はHook設置前の初期化処理です。ネットワーク取得やEXEの確認があるため、描画・tick・native読み取りHookから呼ばないでください。イベント接続まで含むサンプル →

EXPLICIT BY DESIGN

型とエラー

新しい入口では、文字列・数値・boolの並びを用途ごとの型へ置き換えています。これらの型への暗黙変換はありません。

型意味 / 制約例
CommandName1〜64バイト、小文字英数字・_・-、/なしCommandName{"top"}
ArgumentName1〜15バイト、同じASCII文字種ArgumentName{"blocks"}
CommandDescription1024バイト以下、NULなしCommandDescription{"説明"}
BlockIdentifiernamespace:path、小文字ASCIIBlockIdentifier{"minecraft:stone"}
HotbarIndex0〜8。既存HotbarSlotはアイテムの値型HotbarIndex{0}
Yaw / Pitch有限の度数。Pitchは−90〜90Yaw{90.f}, Pitch{0.f}
Reach0より大きく16以下の距離Reach{4.5}
WorldEpoch / TickBudgetワールド世代 / 件数と時間の予算TickBudget{64, 250us}
ReadPolicyCached / FreshReadPolicy::Fresh

不正な値の構築は std::invalid_argument または std::out_of_range。構築は初期化時かnative境界の外で行います。native操作は結果値・エラーコードを返し、コマンドのハンドラー例外はnative境界へ伝播させません。

DECLARE → ARGUMENT → HANDLER

Command Builder

名前・説明・引数・ハンドラーを順に指定します。引数定義とハンドラーが揃うまでは登録可能な CommandDefinition ができません。

#include <bedrock/native_client_commands.hpp>

bedrock::NativeClientCommands commands;
bedrock::CommandDefinition top = bedrock::CommandBuilder::named(bedrock::CommandName{"top"})
    .description(bedrock::CommandDescription{"安全な上方移動"})
    .optionalInteger(bedrock::ArgumentName{"blocks"})
    .handles([](std::optional<int> blocks) -> bedrock::CommandDecision {
        // /top → nullopt、/top 3 → 3
        // コピーした値を自分のtick用キューへ渡す。
        return bedrock::CommandDecision::Accepted;
    });
const bool added = commands.add(std::move(top));

上のハンドラーは型を示す最小例です。実際の処理では、キューに受付できた時だけAcceptedを返してください。必須引数なら .requiredInteger(...) と (int value) -> CommandDecision を組み合わせます。

const bool ready = profiles.prepare(
    {bedrock::Feature::ClientCommands}, options,
    [&](const bedrock::RuntimeProfile& selected, std::string& failure) {
        return commands.load(selected, failure);
    }, error);

// owning clientのLevelTickで、20tick程度の間隔で呼ぶ
const auto registration = commands.update(clientInstance);
// ワールド変更イベント時
commands.reset();
現在のnativeアダプター 整数引数1個に対応。文字列・enum・複数引数・引数なし専用overloadは未対応です。同名コマンドを上書きせず、1 DLLあたり最大32定義。nativeの参照が残るためDLLはpinされます。

コマンド受付は CommandDecision::Accepted / Rejected。登録結果は unavailable / waiting / unchanged / registered / collision / failed。文字列を振り分ける旧 ClientCommands は本体の候補登録を行いません。

ONE OWNER FOR VERSION DATA

プロファイルの取得と更新

  1. ロード中のEXEを識別バージョン名だけに依存せず、ファイルまたはmapped .textのSHA-256とPE形状を確認。
  2. 必要な機能を確認Feature、スキーマ、レイアウトのrevision、candidate利用方針を照合。Gameplay / LevelTick / Input等を要求すると、Hookの解決可否も先に確認します。
  3. アダプターを初期化必要なエントリガード・vtable・ABI形状を確認してからHook設置へ。
  4. 不足時にGitHubへ再照会manifestとwindows-x64.jsonを再取得。失敗時は一致する埋め込み定義を確認。
const bedrock::ProfileRequirements required{
    bedrock::Feature::Gameplay,
    bedrock::Feature::LevelTick,
    bedrock::Feature::World,
    bedrock::Feature::Motion,
    bedrock::Feature::ClientCommands,
    bedrock::Feature::WorldEvents
};
const auto selected = profiles.snapshot();
// 読み取り専用スナップショット。選択後に使用。
const bedrock::Resolver& resolver = selected->resolver();
const bedrock::ProfileSource source = selected->choice().source;
UpdatePolicy動作
CacheFirst通常のSDK選択。キャッシュ・埋め込みを優先し、必要ならネットワーク。機能不足による強制再照会はしない。
RefreshIfNeededアダプターの初期化や必要定義の確認に失敗した場合、GitHubへ再照会する。
ForceRemote最初から再照会経路を使う。既存の同時取得抑制・24時間制限は適用される。

取得先は既存SDKのGitHubカタログに固定。HTTPS、リダイレクト制限、manifestのJSONチェックサム、EXE指紋、PE形状の確認を維持します。更新対象はデータです。稼働中のHookを背景で書き換えず、新しい定義は初期化時に適用します。単なる「最新バージョン」のプロファイルを別ビルドへ流用しません。

CandidatePolicy::VerifiedOnly が既定です。候補のnative機能を利用するModは AllowCandidates を明示します。supports は必要なメタデータの存在確認であり、実機動作の確認ではありません。

READ & PLACE

Worldとブロック配置

const bedrock::BlockPos target{10, 65, 20};
const bedrock::BlockResult block = world.getBlock(target, bedrock::ReadPolicy::Fresh);
if (block) {
    // block.block.identifier / properties / kind
}
const bedrock::BlockSetOptions placement = bedrock::BlockSetBuilder{}
    .slot(bedrock::HotbarIndex{0})
    .orientation(bedrock::Yaw{90.f}, bedrock::Pitch{0.f})
    .reach(bedrock::Reach{4.5})
    .build();
const bedrock::PlacementResult result = world.setBlock(
    target, bedrock::BlockIdentifier{"minecraft:stone"}, placement);

Worldファサードと NativeWorldの両方で型付き呼び出しを使えます。WorldファサードはGameAccessアダプターがブロック機能を提供する必要があります。標準の未実装アダプターはunsupportedを返します。

// NativeWorldを使用する場合、ローカルclientのLevelTick内だけで有効化
using namespace std::chrono_literals;
auto scope = world.tick(clientInstance, event.level,
    bedrock::WorldEpoch{game.worldEpoch()}, bedrock::TickBudget{64, 250us});
if (!scope) return;
// このスコープ内でgetBlock / setBlockを呼ぶ

setBlockはホットバーの実アイテムを選択して本体の配置処理を呼びます。空気への置換・既存ブロックの破壊は未対応。acceptedはnative受付であり、サーバー確定ではありません。後続tickで状態を確認してください。接続状態・階段などの厳密な属性には expect(properties) を指定できます。

エラー：unsupported / wrongThread / staleWorld / budgetExceeded / unavailable / invalidRequest / missingItem / stateMismatch / nativeRejected。

const bedrock::World currentWorld = player.getWorld();
for (const bedrock::Actor& actor : currentWorld.getActors()) {
    const std::string name = actor.getName();
    const auto held = actor.getHeldItem();
    // 返された値だけを別スレッドの処理に渡す
}

Actorのハンドル・RuntimeID・EnTT EntityIDは別物です。ワールド変更時に照合をやり直し、同じIDを別ワールドの同一人物と断定しないでください。nativeアクセスはGameAccess実装が担当します。API名を使っただけで全アダプターが取得能力を持つわけではありません。

OWNERSHIP & THREADS

イベントとスレッド

game.Event.Enum.WorldChange.then([&](const bedrock::WorldChangeEvent& event) {
    commands.reset();
    // 自分のコピー済みキュー・ワールド固有キャッシュを失効させる
});
game.Event.Enum.LevelTick.then([&](const bedrock::LevelTickEvent& event) {
    // 自分のキューから要求を取り出し、予算内でnative操作
});
const auto selected = profiles.snapshot();
hooks = std::make_unique<bedrock::GameHooks>(game);
hooks->installGameplay(selected->resolver(), error);
hooks->installLevelTick(selected->resolver(), error);
hooks->installWorldEvents(selected->resolver(), selected->json(), error);
実行場所処理
初期化スレッド型の構築・ProfileManager・アダプターの準備・Hook接続
owning clientのtickActor / world読取・予測・配置・位置更新
workerコピーした座標・状態・文字列の比較、計画、ログ整形
描画callback準備した描画データの消費。ネットワークや全Actor走査を持ち込まない

イベント・Hookの停止より先に捕捉したオブジェクトを破棄しないでください。時間予算は協調的で、開始済みの本体関数を途中で打ち切る保証はありません。

bedrock::FreeCameraRig rig;

EVOLVE THE ADAPTER

既存コードからの移行

これまで新しい入口
add(name, description, {name, true}, handler)CommandBuilder → 型付き引数 → handles → add(definition)
fetch / JSONキー確認 / refresh / embeddedを各Modへ実装ProfileManager.prepare(requirements, options, adapter, error)
load(json, true, error)load(const RuntimeProfile&, error)
getBlock(pos, true)getBlock(pos, ReadPolicy::Fresh)
setBlock(pos, "minecraft:stone", aggregate)BlockIdentifier + BlockSetBuilder

旧オーバーロードは移行用に維持しています。新コードは型付き入口を使用してください。GameAccessをDLL間で共有する場合は、利用側も同じSDKで再ビルドします。BedrockHookRuntimeのC ABIをこの変更で拡張するものではありません。

JSONで表せるRVA・オフセット差はSDKアダプターで吸収します。引数の渡し方・native構造サイズ・EnTT ABIが変化した場合は、その形に対応するアダプターが必要です。ModへRVAを追加する代わりにSDK側を更新する方針ですが、全将来版のバイナリ互換を保証するものではありません。

GitHub Pagesで公開

このサイトは docs/site 内のHTML・CSS・JavaScriptだけで動作します。外部CDN・Node・生成サービスは不要です。相対リンクなのでGitHub Pagesのリポジトリ配下でも使用できます。

  1. GitHubのSettings → PagesでSourceをGitHub Actionsに設定。
  2. mainの「API documentation」workflowを実行し、publishを有効にします。通常のpushではサイトとC++例をビルドし、公開は手動実行に限定します。
  3. 成功したdeployジョブのURLを開く。
