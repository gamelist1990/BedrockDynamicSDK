# CheckSig auto-dev（実験機能）

`auto-dev`は、現在ロード中のEXEを読み取り、SDK定義の候補と根拠を作る機能です。
探索本体・命令解析・EXE取得はSDKの`auto_profile`にあり、CheckSigは制御と表示を担当します。
今後の版の調査量を減らすための実験です。自動生成だけでABIや全Modの動作を保証しません。

## 有効化

CheckSig起動後、`Documents/PEXData/CheckSig/status.json`の既存JSONに次の値を設定します。

```json
"auto-dev": true
```

既定はfalseです。編集後もCheckSigはこの値を保持します。JSON編集中で読めない場合は上書きしません。
`auto-dev-result`にsnapshot取得、現在の関数、探索件数、完了状態、失敗理由を表示します。
探索は低優先度の専用workerで進み、通常のcommands処理とstatus更新は継続します。

- 停止：`"auto-dev": false`。走査の区切りでキャンセルします。
- 再実行：false→trueに切り替えるか、`"auto-dev-run": 1`を追加し、次は2、3と増やします。
- 任意の参照定義：`"auto-dev-source": "reference/old-windows-x64.json"`。絶対パスも使用できます。
- 新版のバージョン表示：`"auto-dev-version": "1.27.x.y"`。SHAによるEXE識別とは別のラベルです。未知の版のラベルは推測しません。

参照は、明示したsource、内蔵の1.26.60.5/1.26.52.3、ロード済み定義・sourceです。同一EXEの内蔵定義を優先します。
未知の版では既存の版を探索の参考にします。古いオフセットを新しいlayoutとしてコピーしません。
sourceは上限16MiB、statusは4MiBです。通常は追加設定なしで開始できます。

## 出力

`Documents/PEXData/CheckSig/auto-dev/`に、再実行ごとに原子的に上書きします。

| ファイル | 内容 |
| --- | --- |
| `windows-x64.json` | 生成できた部分の定義。対象SHA、関数、生成シグネチャ、合意したslot等 |
| `report.json` | 参照版、各anchorのHit位置・一意性、採否、命令の実値、RIP参照、直接call、RTTI/vtable、導出したフィールド、未解決理由 |
| `report.txt` | 未解決・解析が必要な項目の読みやすい一覧 |
| `error.json` | 中断・失敗の理由とrun。以前の成功出力があっても、今回の成功とは扱わない |
| `live.json` | 完了後、約5秒ごとの実メモリの入口ガード観測 |

必要項目は同梱SDKの調査カタログから列挙します。新しいSDK機能を追加したときはカタログも更新します。
関数が一つも見つからない場合も途中結果は残りますが、その`windows-x64.json`は使用可能なSDKプロファイルではありません。
`profile_has_functions`だけで全機能が揃ったと判断せず、`unresolved`と各layoutの検証状態を確認してください。
file SHA256が取得できない場合は、有効なSDKプロファイルの生成を中止して理由を残します。
3ファイルの書き込みは各ファイル単位で原子的です。全ファイル同時のトランザクションではないため、statusで完了してから取得します。

## 探索と採用条件

1. ロード中EXEのパス・SHA・PE geometryを確認します。通常は前後でSHAを確認したファイルからコードを取得し、既存Hookのジャンプ命令を新しいガードに混ぜません。
2. ファイルとロード中コードの分散サンプルも比較します。暗号化等でファイルのコードを解析できない場合は、範囲を検査したロード中メモリのコピーを使います。パッチ済み入口は不一致として残します。
3. 同一EXEの既存定義なら、入口ガードを再確認して既存の定義・検証履歴を再利用します。これは構造体の寿命を再検証したという意味ではありません。
4. 別EXEなら、独立した2本以上のanchorが、各々一意に同じ`.pdata`関数へ一致することを要求します。元の範囲と発見先の範囲が重なるanchor、Hit上限超過、競合する関数は採用しません。
5. 元定義の`auto_dev_constraints.required_strings`があれば、命令から辿った文字列参照も要求します。先頭4096バイト・256命令内に確認できない場合は手動解析に残します。
6. 対象関数の命令境界を使って新しいシグネチャを作ります。分岐先、immediate、displacementをマスクし、対象EXE内で一意なものだけを保存します。
7. RIP相対参照、直接call先、immediate/変位の実値を根拠として記録します。値の意味が不明な場合は、勝手にメンバー名や「不変値」を割り当てません。
8. RTTIのCompleteObjectLocator・型名・コードポインタを確認してvtableを探します。観測したテーブル間でslotが一致するときだけ候補slotを出し、所有オブジェクトとABIは別途確認します。
9. 識別できた`Level::getPlayerList`が厳密な`mov rax,[rcx+disp32]; ret`形式なら、実際の変位からPlayerList位置を導出します。container/entryの配置まで分かったとは扱いません。

探索は256KiB単位でキャンセルを確認します。関数2048、anchor16/関数、Hit512/anchor、vtable2048等の上限があります。
HDE64で対応できないVEX/EVEXや曖昧な命令は窓の解析を止めます。RET・無条件分岐の後のデータを命令として続けません。
新しいsignatureの一意性は現在のEXEに対する観測です。未来の版でも変化しないことの証明ではありません。

## 自動で確定しないもの

- hidden return、引数の実型、呼出規約、関数の意味が十分に裏付けられないもの。
- Actor/EnTT、PlayerList entry、skin、カメラ等の構造体の意味・寿命。
- 複数候補、inline化、関数統合、vtable slot変更、短すぎるleaf getter。
- 新しいSDKカタログ外の機能、完全な制御フローやデコンパイルが必要な箇所。
- 実際のHook実行、サーバーの受理、表示・復帰・ワールド切替の動作確認。

これらはパス・識別名・理由付きで`unresolved`へ残します。変わらないと断定するゲーム内の定数はありません。
AMD64のpointer size=8のように、検査したアーキテクチャから言える範囲は`invariants`に区別します。

生成結果は自動ロード・自動Hook・自動適用しません。候補を呼び出したり、ゲームメモリへ書き込んだりもしません。
完了後は入口を監視しますが、Hookによる差分を新しい関数と誤認して自動で付け替えることはありません。
未解決の意味・ABI・レイアウトは[更新ガイド](profile-maintenance.md)に従いREA/Ghidraと実機観測で補います。
